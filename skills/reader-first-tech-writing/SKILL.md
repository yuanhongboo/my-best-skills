# 从读者的问题组织技术文章

输入可以是一段代码、一次排障记录或已有草稿。先识别读者已经会什么、读完要判断什么；用户只要审稿时，交付定位明确的意见。只要求局部修订时，在该段及其必要上下文内工作。

1. 写下读者会遇到的具体时刻。例如，刷新后待发送的数据消失了，工程师该从哪里查起？用这个问题筛选素材，先交代可见现象和预期，再进入实现。
2. 拿一个输入贯穿全篇，追踪它经过的关键部件以及某项状态何时变化。只展开会改变读者判断的分支。要讲实现细节，紧接一个读者可以观察或验证的结果。
3. 给关键论断找对应证据。源码能说明某条路径存在；测试限定了被覆盖的输入和断言；现场记录能支持那次运行的结果。主语写成证据能支持的人或系统。另存待补材料的论断，或在正文使用有边界的表述。
4. 选择读图任务。先后顺序画时序，条件分流画决策或流程，静态依赖画组件。图前给出读者要追的对象，图后指出哪个节点改变了结果。能用一段入口代码说明的局部关系，直接展示那段代码。
5. 从头读一遍，请一位初次接触材料的读者回答“输入从哪里来”“哪个选择会改变结果”“如何验证”。修复必须回翻才能理解的术语、突然出现的组件、找不到证据的范围判断。

审稿意见写成“具体段落／读者卡住的动作／最小修订”。例如，“重试策略”段直接出现“重复写入”；可在该段前给出一次网络超时但服务端已保存的场景，让读者理解重复从何而来。
