# 变更风格审查

先选任务起点，以及待比较的已维护同类代码。两者用途不同：前者确定此次交付范围，后者说明项目平常怎么写。新模块缺少历史对应时，选承担同一职责的实现并说明可比范围。用户指定本项目风格时优先服从维护中的约定。

1. 用 `git status --short`、`git diff --name-status <base>` 和 `git ls-files --others --exclude-standard` 查明已提交差异、暂存/未暂存改动与新增文件。保留用户已有的改动和暂存状态，只把任务内的文件计入结论。
2. 按功能角色取样。例如分别给服务、视图组件和测试找对照。检查错误传播、资源生命周期、依赖方向、UI 基础组件、语言资源及测试结构等与改动相关的做法。对怀疑的偏差再查一处同类实例或明确规则，防止把个人习惯写成项目标准。
3. 如已有格式、静态检查或差异度量，用同一基线和范围运行。说明分母、生成文件和忽略项。例如“新增组件中有两处硬编码文案”应附具体行及本项目相邻实现的处理方式。注释密度、复杂度和行数只帮助选择需阅读的地方。
4. 每条发现写明改动位置、对照位置、实际维护成本及最小调整。例如统一到既有错误类型之前，要确认调用方依赖的错误码和失败路径能保留。基线本就存在多种惯例时，用证据说明判断空间。

默认交付审查结果。用户也要求调整时，只改已核实的偏差并按影响复验；不要为达某个指标拆分没有独立职责的代码或删除行为断言。
