# 选择阶段

| 当前请求 | 消费什么 | 写出什么 |
| --- | --- | --- |
| 发起提案 | 谁在什么情况下遇到哪个问题、当前可见行为 | 范围、目标、非目标及待决定事项。区分用户明确要求与调查所得 |
| 明确需求 | 提案、相关现行规格、用户可见入口 | 可观察的成功和失败场景，差异写进规范性行为的唯一正本 |
| 技术设计 | 已确认行为、现有公开接口、状态及副作用的所有者 | 选定方案与舍弃原因、兼容与失败恢复、验证入口。涉及 UI 时固定原型版本、视口、主题及交互状态 |
| 拆实施任务 | 上述输入和版本 | 按一条用户路径拆出第一个可演示结果；给每组任务标明依赖、可写范围、完成证据 |
| 实施 | 已绑定的输入、基线、任务，以及当前工作区中用户已有改动 | 从正式入口接入，先验证一个真实路径和一个关键失败；在现有任务记录留下实现版本和复验入口 |

推导场景时，把操作、观察者、提交时机和不变项写清。例如草稿编辑器承诺“取消不保存”，可以设计三步：先读已保存标题，在编辑中改名并取消，重新打开文档核对原标题和历史条目。若需求没有说明自动保存如何处理，先查现行规格；无法判定时记录为产品决定，其他已确定的场景仍可推进。

没有行为差异的维护任务可以引用仍适用的现有规格，并说明判断依据。工作量小的设计可以很短；让后续实施者看得出准确的输入、分工与验收条件即可。
